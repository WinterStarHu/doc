## 0: INTRODUCTION（引言）

### 0.1 前言

TPC Benchmark™H（TPC-H）是一个**决策支持（decision support）基准**。它由一组面向业务的临时查询（ad-hoc queries）和并发数据修改组成。所选查询与填充数据库的数据具有广泛的行业相关性，同时保持足够的实现简便性。该基准刻画了这样一类决策支持系统：

- 检查大量数据；
- 执行高复杂度查询；
- 给出关键业务问题的答案。

TPC-H 通过在受控条件下对标准数据库执行查询集合，评估各决策支持系统的性能。TPC-H 查询：

- 给出真实业务问题的答案；
- 模拟生成的临时查询（如通过点击式 GUI 界面产生）；
- 比绝大多数 OLTP 事务复杂得多；
- 涵盖丰富的算子与选择性约束；
- 在被测系统的数据库服务器侧产生密集活动；
- 针对符合特定填充与扩展要求的数据库执行；
- 实现上受"与在线生产数据库保持紧密同步"导出的约束。

TPC-H 操作建模如下：

- 数据库每天 24 小时、每周 7 天持续可用，供多终端用户的临时查询和对所有表的数据修改（除偶尔如每月一次的维护时段外）；
- TPC-H 数据库通过持续的刷新函数（将若干影响决策支持数据库某部分的修改批量打包）**带一定延迟地**跟踪 OLTP 数据库的状态；
- 由于 TPC-H 数据库存储的业务数据具有全球性，查询与刷新函数可在任意时刻对数据库执行，尤其相互之间；此外，因查询与刷新函数可能并发执行，这种查询与刷新的混合受特定 ACID 要求约束；
- 为在性能与运维需求间取得最优折中，DBA 可一劳永逸地为查询和刷新函数设定锁定级别与并发调度规则。

运行该基准的最低数据库容纳来自 10,000 个供应商的业务数据，含近一千万行，原始存储约 1GB。合规实现也可使用更大的允许填充规模（如 100GB），见 4.1.3。

TPC-H 报告的性能指标称为 **TPC-H 综合每小时查询性能指标（QphH@Size）**，反映系统处理查询能力的多个方面：执行查询所选的数据库规模、单流提交查询时的查询处理能力、多并发用户提交时的查询吞吐量。TPC-H 性价比指标以 $/kQphH@Size 表示。要符合 TPC-H 标准，对某配置 TPC-H 结果的所有引用都必须包含全部必需的报告组件（见 5.4.6）。TPC 认为，对基于不同数据库规模测得的 TPC-H 结果作比较有误导性，不予鼓励。

TPC-H 数据库必须用市售 DBMS 实现，查询通过动态 SQL 接口执行。规范允许 SQL 变体，不要求实现者完整实现某特定 SQL 标准。

TPC-H 使用的术语和指标与 TPC 及其它机构提出的其它基准相似，但这种术语相似绝不意味着 TPC-H 结果可与其它基准比较。唯一可与 TPC-H 比较的是符合同一修订版的其他 TPC-H 结果。

尽管本基准提供了能代表许多决策支持系统的丰富环境，但并不反映决策支持需求的全部范围。此外，客户能在多大程度上达到厂商报告的结果，高度取决于 TPC-H 与客户应用的近似程度。本基准导出的系统相对性能不一定适用于其它负载或环境，不建议外推到任何其它环境。

基准结果高度依赖负载、具体应用需求及系统设计与实现，相对系统性能会因这些及其它因素而变化。因此，在关键容量规划与/或产品评估决策时，TPC-H 不应替代具体客户应用的基准测试。

允许基准发起者采用多种系统设计，只要遵循第 6 条所述模型即可。实现细节的完整披露报告（FDR，见第 8 条）须随结果一并公开。

注释 1：注释与附录虽为可读性而与正文分离，但仍是标准的一部分，其规定须遵守。

注释 2：部分附录内容以机器可读格式提供，不包含在本文档印刷版中。

### 0.2 通用实现指南

定价规则见位于 www.tpc.org 的 TPC Pricing Specification。

TPC 基准的目的是向行业用户提供相关、客观的性能数据。为此，TPC 基准规范要求基准测试用满足以下条件的系统、产品、技术与定价实现：

- 对用户普遍可用；
- 与该 TPC 基准所建模或代表的市场细分相关（如 TPC-H 建模并代表复杂、高数据量、决策支持环境）；
- 该基准所建模或代表的市场细分中相当数量用户会合理实现。

鼓励使用新的系统、产品、技术（硬件或软件）与定价，只要满足上述要求。明确禁止主要为优化 TPC 基准结果、而对真实应用与环境毫无对应适用性的系统/产品/技术/定价（下称"实现"）。即：凡改善基准结果但不改善真实世界性能或定价的"基准特化（benchmark special）"实现一律禁止。

下列特征用于判断某实现是否为基准特化，不要求每条都满足，而综合权衡证据以识别不可接受的实现；对此复杂问题判断无需绝对确定或超出合理怀疑。须回答的问题是："基于现有证据，证据的明显优势是否表明该实现为基准特化？"

a) 该实现是否普遍可用、有外部文档与支持？
b) 该实现是否对其使用或适用性有重大限制，使其难以用于 TPC 基准之外？
c) 该实现（或其部分）是否与更大产品整合不良？
d) 是否以通常不适用于该基准所代表环境的方式，利用了 TPC 基准的有限性（如查询画像、查询组合、并发/争用、隔离要求等）？
e) 厂商是否不鼓励使用该实现（含未以与其它产品/技术相似方式推广）？
f) 该实现是否要求终端用户、程序员或系统管理员具备不寻常的专业水平？
g) 该实现（含 beta）是否正被基准所代表市场领域的应用购买或使用？有多少站点实现了它？有多少终端用户受益？若当前未被购买或使用，是否有证据表明将被相当数量终端用户站点购买或使用？

注释：本条款所列特征不针对驱动或实现特定层（它们未必是商业软件，有自己的特定要求与限制，见第 6 条）。应使用第 6 条所列特征与禁令判断驱动或实现特定层是否为基准特化。

### 0.3 通用度量指南

TPC 基准结果应是系统性能的准确表示，故度量时须遵循若干指南。度量方法或由规范明确描述，或由测试发起者裁量；未在规范中描述时，所用方法须满足：

- 是公认的工程实践或标准；
- 不夸大结果；
- 度量所用设备按既定质量标准校准；
- 即使 TPC 基准要求未规定，也忠实坦诚地报告结果中的任何异常。

注释：鼓励使用满足上述要求的新方法。

## 1: LOGICAL DATABASE DESIGN（逻辑数据库设计）

### 1.1 业务与应用环境

TPC Benchmark™H 由一组业务查询组成，旨在以代表复杂业务分析应用的方式测试系统功能。这些查询被赋予现实情境，刻画一个**批发供应商**的活动，以助读者直观理解基准各组件。

TPC-H 不代表任何特定业务细分，而是任何须在全球范围内管理、销售或分销产品的行业（如租车、食品分销、零件、供应商等）。TPC-H 不试图成为如何构建实际信息分析应用的模型。

本基准目的在于减少信息分析应用中操作的多样性、同时保留应用的本质性能特征：系统利用水平与操作复杂度。完整管理一个业务分析环境须执行大量类型与复杂度各异的查询；许多查询因运行时长、占用系统资源与执行频率而对性能分析不主要。所选查询具有：高复杂度；使用多种访问方式；临时性；检查可用数据的大比例；彼此互异；含随执行变化的查询参数。

这些所选查询为下列业务分析类别提供答案：定价与促销；供需管理；利润与收入管理；客户满意度研究；市场份额研究；发货管理。

虽侧重信息分析，本基准承认需定期刷新数据库。数据库不是业务操作数据库的一次性快照，也不是 OLTP 应用并发运行的数据库，但须能在 7×24 基础上对所有表支持查询与刷新函数。

本基准虽建模了刷新函数作为数据维护一部分的业务环境，但基准实际要求的刷新函数并不试图建模业务环境的这一方面，其目的是展示 DBMS 的更新功能、同时评估辅助数据结构（如二级索引）维护的恰当性能代价。

注释：本基准不含验证数据库持续可用性或使基准配置适合 7×24 运行的特定系统特性的测试或度量；提及持续可用与 7×24 仅为更完整描绘预期的决策支持环境。只要满足本规范全部要求，可用性低于 7×24 的配置也能产出合规基准结果。

[图 1：TPC-H 业务环境（原文 ASCII 图保留）]

其它 TPC 基准建模业务环境中实时执行事务的运营端；而 TPC-H 建模业务环境中计算趋势、产出精炼数据以支持稳健业务决策的分析端。OLTP 基准中原始数据从各源流入 OLTP 数据库并维护一段时间；TPC-H 中对 DSS 数据库执行周期性刷新函数，其内容由各决策者或代表各决策者查询。

#### 1.4.2 约束

约束的使用是可选的，且仅限于主键、外键、check 与 not null 约束。若使用约束须满足：

- 须用 SQL 指定，无特定实现要求（CREATE TABLE、ALTER TABLE、CREATE UNIQUE INDEX、CREATE TRIGGER 均有效）；
- 约束须在语句级或事务级强制执行；
- 所有已定义约束须在加载测试完成前强制执行并校验（见 5.1.1.2）。

1.4.2.1 任意列可用 NOT NULL 属性。
1.4.2.2 1.4.1 中列为"Primary Key"的下列列/列组可定义为主键约束（用 PRIMARY KEY 子句或等价语法）：P_PARTKEY；S_SUPPKEY；(PS_PARTKEY, PS_SUPPKEY)；C_CUSTKEY；O_ORDERKEY；(L_ORDERKEY, L_LINENUMBER)；N_NATIONKEY；R_REGIONKEY。主键约束只能对上述列定义。
1.4.2.3 1.4.1 注释中标为"Foreign Key"的列可定义为外键约束，无特定要求使用参照动作（RESTRICT/CASCADE/NO ACTION 等）。若实现定义了任一外键约束，则须定义下列全部外键约束：S_NATIONKEY(→N_NATIONKEY)、PS_PARTKEY(→P_PARTKEY)、PS_SUPPKEY(→S_SUPPKEY)、C_NATIONKEY(→N_NATIONKEY)、O_CUSTKEY(→C_CUSTKEY)、L_ORDERKEY(→O_ORDERKEY)、L_PARTKEY(→P_PARTKEY)、L_SUPPKEY(→S_SUPPKEY)、(L_PARTKEY,L_SUPPKEY)(→PS_PARTKEY,PS_SUPPKEY)、N_REGIONKEY(→R_REGIONKEY)。外键约束只能对上述列定义。
1.4.2.4 Check 约束：可定义 check 约束限制数据库内容；为支持演进变更，check 约束不得依赖对各列枚举域的知识。允许的 check 约束：
  1. 正键：P_PARTKEY/S_SUPPKEY/C_CUSTKEY/PS_PARTKEY/R_REGIONKEY/N_NATIONKEY >= 0
  2. 开区间约束：P_SIZE/P_RETAILPRICE/PS_AVAILQTY/PS_SUPPLYCOST/O_TOTALPRICE/L_QUANTITY/L_EXTENDEDPRICE/L_TAX >= 0
  3. 闭区间约束：L_DISCOUNT between 0.00 and 1.00
  4. 多列约束：L_SHIPDATE <= L_RECEIPTDATE
注释：上述约束仅依赖 1.2 的模式图与 1.4 的描述，不依赖 4.2 所规定的数据填充的显式知识。

### 1.5 实现规则

1.5.1 数据库须用市售 DBMS 实现。
1.5.2 允许数据库内记录的物理聚簇，只要该聚簇不改变各表的逻辑独立性。（注释：意在允许物理设计灵活、同时保持所有表的严格逻辑视图。）
1.5.3 加载测试结束时，所有表的行数须恰好等于第 4 条为扩展因子 SF 与数据库填充所定义的数量。
1.5.4 允许对基表或数据库指令创建的辅助结构（见 1.5.7）进行**水平分区**：表或辅助结构中的行组可分配到不同文件/磁盘/区。若此分配是表或辅助结构中数据的函数，则须基于某分区字段的值。分区字段须且仅须为下列之一：1.4.2.2 列出的列或列组（无论是否定义为主键约束）；1.4.2.3 列出的列或列组（无论是否定义为外键约束）；1.3 定义中具有 date 数据类型的列。
某些分区方案需用指定分区字段显式值的指令，若用须满足：不得依赖表中存储数据的任何知识（仅限分区字段列的最小/最大值，见 4.2.3）；在整数除法限制内须定义每个分区接纳分区列最小最大值之间范围的等份；基于日期的分区可按天/周/月/年的整数粒度等大小划分（如 30 天、4 周、1 月、1 年），非天粒度时分区边界可超出 4.2.3 所定数据特征边界；指令须允许插入超出最小最大值范围的分区列值（见 1.5.13）。
基表或辅助结构的多级分区仅当每级满足上述条件且每级仅引用一个上述分区字段时允许；若实现须披露细节。
1.5.5 数据在持久介质上的物理放置不可审计。**禁止**显式垂直分区数据的 SQL DDL，行须逻辑上表现为原子的列集合。（注释：不依赖显式分区指令的垂直分区允许；显式分区指令指将一行中列组分配到与该行其它列不同文件/磁盘/区的指令。）
1.5.6 除 1.5.7 规定外，不允许数据库对象（表、行、列）的逻辑复制。表的辅助数据结构的物理实现可涉及从表复制选定数据，前提：所有复制数据由 DBMS/OS/硬件管理；所有复制对所有数据操作透明；更新事务提交时数据修改反映到所有逻辑副本；所有副本随时保持完整 ACID 特性（见第 3 条）。
1.5.7 构成基表一列或多列数据逻辑复制的辅助数据结构（如索引、物化视图、汇总表、用于强制关系完整性约束的结构）须符合 1.5.6 规定，其定义创建指令受下列限制：每条指令最多引用一个基表、不得引用其它辅助结构；每条指令仅引用一个——1.4.2.2 列的列/列组（无论是否主键约束）、1.4.2.3 列的列/列组（无论是否外键约束）、或 1.3 中 date 类型列；每条指令可含显式允许列上的函数或表达式。TPC-H 脚本中禁止任何导致在辅助结构物化上述显式允许列之外列（或列上函数）的指令（DDL/会话选项/全局配置参数等），也禁止导致物化来自多表列的辅助结构。
注释：合规指令生成的辅助结构实现通常含指向基表行的内嵌指针或引用；透明使用 row ID 或基表主键值都可接受。辅助结构所需透明内嵌主键值的生成属主键列的允许物化。主键/外键列见 1.4.1。
1.5.8 表名应与 1.4.1 一致；与保留字冲突时可用分隔标识符或有意义的别名。
1.5.9 每张表的列集须包含 1.4 定义的全部列，不得增加列，但列顺序不限。
1.5.10 列名须与 1.4 一致。
1.5.11 每列须逻辑离散、可由数据管理器独立访问（如 C_ADDRESS 与 C_PHONE 不能实现为单个离散列 C_DATA 的两部分）。
1.5.12 每列须可由数据管理器作为单列访问（如 P_TYPE 不能实现为两离散列 P_TYPE1/P_TYPE2）。
1.5.13 数据库须允许插入符合 1.3 与 1.4 数据类型及可选约束定义的任意数据值。
注释1：虽刷新函数（见 2.5）不插入任意值、不修改所有表，但所有表须在整个性能测试期间可修改。
注释2：意在防止数据库模式定义不当利用数据库有限数据填充（另见 0.2 与 5.2.7）。

### 1.6 数据访问透明性要求

1.6.1 数据访问透明性是系统从查询文本中移除对分区数据位置与访问机制知识的特性。无有限测试序列能证明系统支持完全数据访问透明。下列要求描述建立系统提供透明数据访问所需的最小能力。使用水平分区的实现须满足 1.6.2 与 1.6.3 的透明数据访问要求。（注释：要求数据访问由市售层——交互式 SQL 接口、DBMS、OS、硬件或其组合——直接透明提供。）
1.6.2 1.4 所述各表须能以与表分区无关的名称标识。可执行查询文本（见 2.1.1.2）中所有数据操作只能用这些名称。
1.6.3 用满足 1.6.2 的名称，任意非 TPC-H 查询须能引用任意行或列集合：由底层 DBMS 支持的任意条件标识；用 1.6.2 所述名称、对所有表使用相同数据操作语义与语法。（注释：每个 TPC-H 查询使用通用机制访问数据库数据。）

## 2: QUERIES AND REFRESH FUNCTIONS（查询与刷新函数）

本条描述作为 TPC-H 基准一部分须执行的 22 条决策支持查询与 2 个数据库刷新函数。

### 2.1 查询通用要求与定义（要点）

- 每条查询有功能定义（SQL）、替换参数（substitution parameters，运行时随机生成）、查询验证（用固定参数对资格库产生固定输出）、样例输出。SQL 与替换参数、验证值见英文原版。
- 查询文本须用动态 SQL 执行；替换参数在每次执行前随机生成并代入。
- 22 条查询的顺序在吞吐测试中由驱动随机化。

### 2.2 查询合规 / 2.3 查询验证（要点）

- 合规实现的可执行查询文本须取自功能定义或经批准的查询变体（附录 B），不得改变语义。
- 各查询须能用指定替换参数对资格数据库产出与附录 F 参考数据集一致的验证输出。

### 2.4 查询定义

下为 22 条查询的**业务意图精译**（SQL/替换参数/验证/样例输出见英文原版 `T/md/TPC-H_v3.0.1.md` 2.4.N.2–2.4.N.5）。

#### Q1 Pricing Summary Report Query（定价汇总报告查询）
摘要：报告已计费、已发货、已退货的业务量。
业务意图：对截至某给定日期（该日期在数据库最大发货日期之后 60–120 天内）所有已发货的行项，提供汇总定价报告。列出：扩展价合计、折扣后扩展价合计、折扣后扩展价加税合计、平均数量、平均扩展价、平均折扣，按 RETURNFLAG 与 LINESTATUS 分组并按其升序排列，并含每组行项计数。

#### Q2 Minimum Cost Supplier Query（最低成本供应商查询）
摘要：为给定区域内的给定零件找出应选哪个供应商下单。
业务意图：在给定区域内，对每种特定类型与尺寸的零件，找出能以最低成本供货的供应商。若该区域内多个供应商以相同（最低）成本供应该零件类型与尺寸，则列出账户余额最高的前 100 个供应商的零件。对每个供应商列出：账户余额、名称、国家；零件号与制造商；供应商地址、电话、注释。

#### Q3 Shipping Priority Query（发货优先级查询）
摘要：检索价值最高的 10 个未发货订单。
业务意图：检索截至某日期尚未发货的订单中、收入最大者的发货优先级与潜在收入（定义为 l_extendedprice*(1-l_discount) 之和），按收入降序列出；若未发货订单超过 10 个，仅列收入最大的 10 个。

#### Q4 Order Priority Checking Query（订单优先级检查查询）
摘要：评估订单优先级系统运作情况及客户满意度。
业务意图：统计给定年/季度中、客户至少一个行项晚于承诺日期收到的订单数，按订单优先级升序列出各优先级的此类订单数。

#### Q5 Local Supplier Volume Query（本地供应商业务量查询）
摘要：列出通过本地供应商完成的业务量。
业务意图：对给定区域内每个国家，列出由该国客户下单、该国供应商供货的行项交易所产生的业务量（定义为 sum(l_extendedprice*(1-l_discount))），用于决定是否在该区域设立本地分销中心；只考虑给定年订购的零件；按业务量降序列出国家与业务量。

#### Q6 Forecasting Revenue Change Query（收入变化预测查询）
摘要：量化消除某些公司折扣带来的收入增量。
业务意图：考虑给定年内发货、折扣在 DISCOUNT-0.01 与 DISCOUNT+0.01 之间的行项，列出去掉这些折扣、且 l_quantity 小于 quantity 的行项将带来的总收入增量（增量 = 符合条件的行项的 l_extendedprice*l_discount 之和）。

#### Q7 Volume Shipping Query（货运量查询）
摘要：确定特定国家间货运货物价值，用于重谈运费。
业务意图：对两个给定国家，找出 1995 与 1996 年间由一国供应商运往另一国客户的行项产生的折扣后总收入；按供应商国、客户国、年（均升序）列出。

#### Q8 National Market Share Query（国家市场份额查询）
摘要：确定给定区域内某给定国家在某产品上的两年市场份额变化。
业务意图：给定区域内某国的市场份额 = 该国供应商所供、该区域指定类型产品收入（sum[l_extendedprice*(1-l_discount)]）占该区域该类产品总收入的比例；查询给出 1995 与 1996 年（此顺序）的值。

#### Q9 Product Type Profit Measure Query（产品类型利润度量查询）
摘要：按供应商国家与年，确定某零件系列的利润。
业务意图：对每个国家与每年，找出该年订购的、名称含指定子串且由该国供应商供货的零件的利润（定义为 sum[(l_extendedprice*(1-l_discount)) - (ps_supplycost*l_quantity)]）；按国家字母升序、每年按年降序列出。

#### Q10 Returned Item Reporting Query（退货报告查询）
摘要：识别可能在收到的零件上有问题的客户。
业务意图：找出给定季度内因退货对收入损失影响最大的前 20 个客户；只考虑该季度订购的零件；列出客户名、地址、国家、电话、账户余额、注释、损失收入（定义为符合条件的行项 sum(l_extendedprice*(1-l_discount))），按损失收入降序。

#### Q11 Important Stock Identification Query（重要库存识别查询）
摘要：找出给定国家供应商库存中最重要的子集。
业务意图：扫描给定国家供应商的可用库存，找出占所有可用零件总价值显著比例的全部零件，按价值降序列出零件号与价值。

#### Q12 Shipping Modes and Order Priority Query（运输模式与订单优先级查询）
摘要：判断选用较便宜运输模式是否影响了关键优先级订单。
业务意图：按运输模式统计给定年客户实际收到的行项中、属于 l_receiptdate 晚于 l_commitdate 且为两种指定运输模式的行项数（只计实际在 l_commitdate 前发货者），并将迟到行项分为优先级 URGENT/HIGH 与其它两组。

#### Q13 Customer Distribution Query（客户分布查询）
摘要：探查客户与其订单规模的关系。
业务意图：按客户下单数分布客户（含过去/现在都无订单的客户），统计并报告无订单、有 1/2/3… 单订单的客户数；并校验所计订单不落入订单注释列中特定模式标识的特殊类别。

#### Q14 Promotion Effect Query（促销效果查询）
摘要：监测对促销（如电视广告或专项活动）的市场反应。
业务意图：确定给定年月中、由促销零件产生的收入占比；只考虑该月实际发货的零件；收入定义为 (l_extendedprice*(1-l_discount))。

#### Q15 Top Supplier Query（顶级供应商查询）
摘要：确定顶级供应商以奖励、给更多业务或特别表彰。
业务意图：找出给定年/季度发货零件中对总收入贡献最大的供应商；并列时列出贡献等于最大值的所有供应商，按供应商号排序。

#### Q16 Parts/Supplier Relationship Query（零件/供应商关系查询）
摘要：找出有多少供应商能供具有给定属性的零件。
业务意图：统计能供应满足某特定客户需求的零件的供应商数：客户需要 8 种不同尺寸的零件，且不得为给定类型、给定品牌、不得来自在 BBB 有投诉记录的供应商；结果按计数降序、品牌/类型/尺寸升序。

#### Q17 Small-Quantity-Order Revenue Query（小批量订单收入查询）
摘要：若不再为小批量订单供货，平均年收入会损失多少。
业务意图：考虑给定品牌、给定容器类型的零件，确定 7 年数据库中所有订单（已发生与待处理）此类零件的平均行项数量；若不再接受数量低于该平均值 20% 的此类零件订单，平均年毛（未折扣）收入损失是多少？

#### Q18 Large Volume Customer Query（大客户查询）
摘要：按是否下过大数量订单对客户排名。
业务意图：找出曾下过大数量订单的前 100 名客户，列出客户名、客户号、订单号、日期、总价与订单数量。

#### Q19 Discounted Revenue Query（折扣收入查询）
摘要：报告经空运、本人签收的选定零件销售的折扣后总收入。
业务意图：对空运且本人签收的三类不同零件订单，按特定品牌组合、容器清单与尺寸范围选取零件，找出折扣后总收入。

#### Q20 Potential Part Promotion Query（潜在零件促销查询）
摘要：识别特定国家中、有可促销候选零件的供应商。
业务意图：识别给定国家中、某给定零件库存过剩（过剩 = 超过该供应商该年该国所运同类零件的 50%）的供应商；只考虑名称符合某命名约定的零件。

#### Q21 Suppliers Who Kept Orders Waiting Query（延误订单的供应商查询）
摘要：识别未能及时发货的供应商。
业务意图：对给定国家，识别其产品属于多供应商订单（当前状态为 'F'）且是唯一未按承诺日期交货的供应商。

#### Q22 Global Sales Opportunity Query（全球销售机会查询）
摘要：识别可能有下单意向的客户所在地区。
业务意图：统计特定国家代码范围内、7 年未下单但账户余额高于平均"正"余额的客户数，并反映余额规模；国家代码定义为 c_phone 前两个字符。

### 2.5–2.8 刷新函数（要点）

- 2.5 刷新函数通用要求：刷新函数修改决策支持数据库以跟踪 OLTP 变更；两个刷新函数 RF1（新增销售）与 RF2（旧销售删除）。
- 2.6 RF1（New Sales Refresh Function）：将代表新销售订单及其行项的记录插入 ORDERS 与 LINEITEM。
- 2.7 RF2（Old Sales Refresh Function）：从 ORDERS 与 LINEITEM 删除代表最旧销售订单的记录。
- 2.8 数据库演进过程：刷新函数迭代应用使数据库规模随时间增长；每次刷新流 = 先 RF1 后 RF2。

> 各刷新函数的精确参数、输入数据与规则见英文原版 2.5–2.8。

## 3: THE ACID PROPERTIES（ACID 特性，要点）

TPC-H 须在测试数据库上满足 ACID（原子性、一致性、隔离性、持久性）要求。规范给出具体的事务测试以验证：

- 3.2 原子性：定义若干事务（如付款、订单状态、发货、级别变更、库存），要求事务或全部完成或全部回滚，不留部分结果；并给出在失败注入下验证原子性的测试场景。
- 3.3 一致性：数据库须满足 1.4.2 的约束（主键/外键/check）及若干业务一致性条件（如 L_SHIPDATE ≤ L_RECEIPTDATE、订单/行项参照完整性、账户余额一致性），验证测试检查事务前后约束均成立。
- 3.4 隔离性：用一组并发事务组合（在两张终端表上交错执行付款、订单状态、发货等）验证隔离级别，要求并发执行结果与某种串行化等价（避免脏读/不可重复读/幻读导致的不一致）。
- 3.5 持久性：提交事务的修改须在数据库崩溃、进程失败、介质故障后仍能恢复；测试包括断电（SUT 断电）后验证已提交数据不丢。

具体事务定义、SQL 与测试场景见英文原版 3.2–3.5。

## 5: PERFORMANCE METRICS AND EXECUTION RULES（性能指标与执行规则）

### 5.1 术语（要点）

- 一次"运行（run）"= 一次 Power 测试 + 一次 Throughput 测试；性能测试须执行两次运行（Run 1、Run 2），报告较好者。
- Load Test：数据库加载；Performance Test：Power + Throughput。

### 5.2 配置规则（要点）

- 须用市售、普遍可用、有支持的配置；定价配置须可交付；不得为基准特化（见 0.2）。

### 5.3 执行规则（要点）

- 5.3.3 **Power 测试**：单会话单查询流，按固定顺序执行 22 条查询与 2 个刷新函数（RF1、RF2），记录每条查询与刷新的时间间隔 QI(i,0)、RI(j,0)。
- 5.3.4 **Throughput 测试**：S 个并发查询流，每流 22 条查询，与一个并发刷新流；度量区间 Ts 内执行的总查询数。S（查询流数）随 SF 增大（SF 越大 S 越多），见 5.3.4 对应表。
- Power 与 Throughput 须在相同硬件/软件条件下执行；刷新函数与查询并发。

### 5.4 指标

TPC-H 主指标：

- **QphH@Size**（TPC-H 综合每小时查询性能指标，5.4.3）：性能指标。
- **$/kQphH@Size**（TPC-H 性价比，5.4.4）：价格/性能。
- 系统可用日期（见 TPC Pricing Specification 0 条）。
- 选报 TPC-Energy 时另有 Watts/kQphH@Size 能耗指标。
次级量（须在数值量摘要披露）：TPC-H Power、TPC-H Throughput、S（吞吐测试查询流数）。

#### 5.4.1 TPC-H Power@Size

由 Power 测试结果计算查询处理能力，定义为时间间隔几何均值的倒数：

```
                 3600 * SF
TPC-H Power@Size = ----------------------------------
                   24
                   ∏  QI(i,0)  *  ∏  RI(j,0)
                  i=1..22        j=1..2
```
其中 QI(i,0) 为 Power 测试中查询 Q_i 的计时（秒），RI(j,0) 为刷新函数 RFj 的计时（秒），SF 为扩展因子，Size 为所选数据库规模。单位：查询/小时 × 扩展因子，保留 1 位小数。
等价：`3600 * exp(-(1/24)·Σ ln(QI(i,0)) - Σln(RI(j,0))) * SF`（几何均值）。若最长/最短查询计时比 > 1000，则小于 max/1000 的计时须上调为 max/1000。

#### 5.4.2 TPC-H Throughput@Size

由 Throughput 测试计算：
```
TPC-H Throughput@Size = (S * 22 * 3600) / Ts * SF
```
其中 Ts 为度量区间（秒），S 为吞吐测试查询流数，SF 为扩展因子。单位：查询/小时 × 扩展因子。

#### 5.4.3 QphH@Size（综合指标）

```
QphH@Size = sqrt( Power@Size * Throughput@Size )
```
即 Power 与 Throughput 的几何均值，综合反映单流查询处理能力与多流吞吐。

#### 5.4.4 性价比

```
$/kQphH@Size = 系统价格(美元) / (QphH@Size / 1000)
```
（价格按 TPC Pricing Specification；QphH@Size 以千为单位。）
