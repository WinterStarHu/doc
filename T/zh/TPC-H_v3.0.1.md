## 0: INTRODUCTION（引言）

### 0.1 前言

TPC Benchmark™H（TPC-H）是一个**决策支持（decision support）基准**。它由一组面向业务的临时查询（ad-hoc queries）和并发数据修改组成。所选查询与填充数据库的数据具有广泛的行业相关性，同时保持足够的实现简便性。该基准刻画了这样一类决策支持系统：

- 检查大量数据；
- 执行高复杂度查询；
- 给出关键业务问题的答案。

TPC-H 通过在受控条件下对标准数据库执行查询集合，评估各决策支持系统的性能。TPC-H 查询：

- 给出真实业务问题的答案；
- 模拟生成的临时查询（如通过点击式 GUI 界面产生）；
- 比绝大多数 OLTP 事务复杂得多；
- 涵盖丰富的算子与选择性约束；
- 在被测系统的数据库服务器侧产生密集活动；
- 针对符合特定填充与扩展要求的数据库执行；
- 实现上受"与在线生产数据库保持紧密同步"导出的约束。

TPC-H 操作建模如下：

- 数据库每天 24 小时、每周 7 天持续可用，供多终端用户的临时查询和对所有表的数据修改（除偶尔如每月一次的维护时段外）；
- TPC-H 数据库通过持续的刷新函数（将若干影响决策支持数据库某部分的修改批量打包）**带一定延迟地**跟踪 OLTP 数据库的状态；
- 由于 TPC-H 数据库存储的业务数据具有全球性，查询与刷新函数可在任意时刻对数据库执行，尤其相互之间；此外，因查询与刷新函数可能并发执行，这种查询与刷新的混合受特定 ACID 要求约束；
- 为在性能与运维需求间取得最优折中，DBA 可一劳永逸地为查询和刷新函数设定锁定级别与并发调度规则。

运行该基准的最低数据库容纳来自 10,000 个供应商的业务数据，含近一千万行，原始存储约 1GB。合规实现也可使用更大的允许填充规模（如 100GB），见 4.1.3。

TPC-H 报告的性能指标称为 **TPC-H 综合每小时查询性能指标（QphH@Size）**，反映系统处理查询能力的多个方面：执行查询所选的数据库规模、单流提交查询时的查询处理能力、多并发用户提交时的查询吞吐量。TPC-H 性价比指标以 $/kQphH@Size 表示。要符合 TPC-H 标准，对某配置 TPC-H 结果的所有引用都必须包含全部必需的报告组件（见 5.4.6）。TPC 认为，对基于不同数据库规模测得的 TPC-H 结果作比较有误导性，不予鼓励。

TPC-H 数据库必须用市售 DBMS 实现，查询通过动态 SQL 接口执行。规范允许 SQL 变体，不要求实现者完整实现某特定 SQL 标准。

TPC-H 使用的术语和指标与 TPC 及其它机构提出的其它基准相似，但这种术语相似绝不意味着 TPC-H 结果可与其它基准比较。唯一可与 TPC-H 比较的是符合同一修订版的其他 TPC-H 结果。

尽管本基准提供了能代表许多决策支持系统的丰富环境，但并不反映决策支持需求的全部范围。此外，客户能在多大程度上达到厂商报告的结果，高度取决于 TPC-H 与客户应用的近似程度。本基准导出的系统相对性能不一定适用于其它负载或环境，不建议外推到任何其它环境。

基准结果高度依赖负载、具体应用需求及系统设计与实现，相对系统性能会因这些及其它因素而变化。因此，在关键容量规划与/或产品评估决策时，TPC-H 不应替代具体客户应用的基准测试。

允许基准发起者采用多种系统设计，只要遵循第 6 条所述模型即可。实现细节的完整披露报告（FDR，见第 8 条）须随结果一并公开。

注释 1：注释与附录虽为可读性而与正文分离，但仍是标准的一部分，其规定须遵守。

注释 2：部分附录内容以机器可读格式提供，不包含在本文档印刷版中。

### 0.2 通用实现指南

定价规则见位于 www.tpc.org 的 TPC Pricing Specification。

TPC 基准的目的是向行业用户提供相关、客观的性能数据。为此，TPC 基准规范要求基准测试用满足以下条件的系统、产品、技术与定价实现：

- 对用户普遍可用；
- 与该 TPC 基准所建模或代表的市场细分相关（如 TPC-H 建模并代表复杂、高数据量、决策支持环境）；
- 该基准所建模或代表的市场细分中相当数量用户会合理实现。

鼓励使用新的系统、产品、技术（硬件或软件）与定价，只要满足上述要求。明确禁止主要为优化 TPC 基准结果、而对真实应用与环境毫无对应适用性的系统/产品/技术/定价（下称"实现"）。即：凡改善基准结果但不改善真实世界性能或定价的"基准特化（benchmark special）"实现一律禁止。

下列特征用于判断某实现是否为基准特化，不要求每条都满足，而综合权衡证据以识别不可接受的实现；对此复杂问题判断无需绝对确定或超出合理怀疑。须回答的问题是："基于现有证据，证据的明显优势是否表明该实现为基准特化？"

a) 该实现是否普遍可用、有外部文档与支持？
b) 该实现是否对其使用或适用性有重大限制，使其难以用于 TPC 基准之外？
c) 该实现（或其部分）是否与更大产品整合不良？
d) 是否以通常不适用于该基准所代表环境的方式，利用了 TPC 基准的有限性（如查询画像、查询组合、并发/争用、隔离要求等）？
e) 厂商是否不鼓励使用该实现（含未以与其它产品/技术相似方式推广）？
f) 该实现是否要求终端用户、程序员或系统管理员具备不寻常的专业水平？
g) 该实现（含 beta）是否正被基准所代表市场领域的应用购买或使用？有多少站点实现了它？有多少终端用户受益？若当前未被购买或使用，是否有证据表明将被相当数量终端用户站点购买或使用？

注释：本条款所列特征不针对驱动或实现特定层（它们未必是商业软件，有自己的特定要求与限制，见第 6 条）。应使用第 6 条所列特征与禁令判断驱动或实现特定层是否为基准特化。

### 0.3 通用度量指南

TPC 基准结果应是系统性能的准确表示，故度量时须遵循若干指南。度量方法或由规范明确描述，或由测试发起者裁量；未在规范中描述时，所用方法须满足：

- 是公认的工程实践或标准；
- 不夸大结果；
- 度量所用设备按既定质量标准校准；
- 即使 TPC 基准要求未规定，也忠实坦诚地报告结果中的任何异常。

注释：鼓励使用满足上述要求的新方法。

## 1: LOGICAL DATABASE DESIGN（逻辑数据库设计）

### 1.1 业务与应用环境

TPC Benchmark™H 由一组业务查询组成，旨在以代表复杂业务分析应用的方式测试系统功能。这些查询被赋予现实情境，刻画一个**批发供应商**的活动，以助读者直观理解基准各组件。

TPC-H 不代表任何特定业务细分，而是任何须在全球范围内管理、销售或分销产品的行业（如租车、食品分销、零件、供应商等）。TPC-H 不试图成为如何构建实际信息分析应用的模型。

本基准目的在于减少信息分析应用中操作的多样性、同时保留应用的本质性能特征：系统利用水平与操作复杂度。完整管理一个业务分析环境须执行大量类型与复杂度各异的查询；许多查询因运行时长、占用系统资源与执行频率而对性能分析不主要。所选查询具有：高复杂度；使用多种访问方式；临时性；检查可用数据的大比例；彼此互异；含随执行变化的查询参数。

这些所选查询为下列业务分析类别提供答案：定价与促销；供需管理；利润与收入管理；客户满意度研究；市场份额研究；发货管理。

虽侧重信息分析，本基准承认需定期刷新数据库。数据库不是业务操作数据库的一次性快照，也不是 OLTP 应用并发运行的数据库，但须能在 7×24 基础上对所有表支持查询与刷新函数。

本基准虽建模了刷新函数作为数据维护一部分的业务环境，但基准实际要求的刷新函数并不试图建模业务环境的这一方面，其目的是展示 DBMS 的更新功能、同时评估辅助数据结构（如二级索引）维护的恰当性能代价。

注释：本基准不含验证数据库持续可用性或使基准配置适合 7×24 运行的特定系统特性的测试或度量；提及持续可用与 7×24 仅为更完整描绘预期的决策支持环境。只要满足本规范全部要求，可用性低于 7×24 的配置也能产出合规基准结果。

[图 1：TPC-H 业务环境（原文 ASCII 图保留）]

其它 TPC 基准建模业务环境中实时执行事务的运营端；而 TPC-H 建模业务环境中计算趋势、产出精炼数据以支持稳健业务决策的分析端。OLTP 基准中原始数据从各源流入 OLTP 数据库并维护一段时间；TPC-H 中对 DSS 数据库执行周期性刷新函数，其内容由各决策者或代表各决策者查询。

#### 1.4.2 约束

约束的使用是可选的，且仅限于主键、外键、check 与 not null 约束。若使用约束须满足：

- 须用 SQL 指定，无特定实现要求（CREATE TABLE、ALTER TABLE、CREATE UNIQUE INDEX、CREATE TRIGGER 均有效）；
- 约束须在语句级或事务级强制执行；
- 所有已定义约束须在加载测试完成前强制执行并校验（见 5.1.1.2）。

1.4.2.1 任意列可用 NOT NULL 属性。
1.4.2.2 1.4.1 中列为"Primary Key"的下列列/列组可定义为主键约束（用 PRIMARY KEY 子句或等价语法）：P_PARTKEY；S_SUPPKEY；(PS_PARTKEY, PS_SUPPKEY)；C_CUSTKEY；O_ORDERKEY；(L_ORDERKEY, L_LINENUMBER)；N_NATIONKEY；R_REGIONKEY。主键约束只能对上述列定义。
1.4.2.3 1.4.1 注释中标为"Foreign Key"的列可定义为外键约束，无特定要求使用参照动作（RESTRICT/CASCADE/NO ACTION 等）。若实现定义了任一外键约束，则须定义下列全部外键约束：S_NATIONKEY(→N_NATIONKEY)、PS_PARTKEY(→P_PARTKEY)、PS_SUPPKEY(→S_SUPPKEY)、C_NATIONKEY(→N_NATIONKEY)、O_CUSTKEY(→C_CUSTKEY)、L_ORDERKEY(→O_ORDERKEY)、L_PARTKEY(→P_PARTKEY)、L_SUPPKEY(→S_SUPPKEY)、(L_PARTKEY,L_SUPPKEY)(→PS_PARTKEY,PS_SUPPKEY)、N_REGIONKEY(→R_REGIONKEY)。外键约束只能对上述列定义。
1.4.2.4 Check 约束：可定义 check 约束限制数据库内容；为支持演进变更，check 约束不得依赖对各列枚举域的知识。允许的 check 约束：
  1. 正键：P_PARTKEY/S_SUPPKEY/C_CUSTKEY/PS_PARTKEY/R_REGIONKEY/N_NATIONKEY >= 0
  2. 开区间约束：P_SIZE/P_RETAILPRICE/PS_AVAILQTY/PS_SUPPLYCOST/O_TOTALPRICE/L_QUANTITY/L_EXTENDEDPRICE/L_TAX >= 0
  3. 闭区间约束：L_DISCOUNT between 0.00 and 1.00
  4. 多列约束：L_SHIPDATE <= L_RECEIPTDATE
注释：上述约束仅依赖 1.2 的模式图与 1.4 的描述，不依赖 4.2 所规定的数据填充的显式知识。

### 1.5 实现规则

1.5.1 数据库须用市售 DBMS 实现。
1.5.2 允许数据库内记录的物理聚簇，只要该聚簇不改变各表的逻辑独立性。（注释：意在允许物理设计灵活、同时保持所有表的严格逻辑视图。）
1.5.3 加载测试结束时，所有表的行数须恰好等于第 4 条为扩展因子 SF 与数据库填充所定义的数量。
1.5.4 允许对基表或数据库指令创建的辅助结构（见 1.5.7）进行**水平分区**：表或辅助结构中的行组可分配到不同文件/磁盘/区。若此分配是表或辅助结构中数据的函数，则须基于某分区字段的值。分区字段须且仅须为下列之一：1.4.2.2 列出的列或列组（无论是否定义为主键约束）；1.4.2.3 列出的列或列组（无论是否定义为外键约束）；1.3 定义中具有 date 数据类型的列。
某些分区方案需用指定分区字段显式值的指令，若用须满足：不得依赖表中存储数据的任何知识（仅限分区字段列的最小/最大值，见 4.2.3）；在整数除法限制内须定义每个分区接纳分区列最小最大值之间范围的等份；基于日期的分区可按天/周/月/年的整数粒度等大小划分（如 30 天、4 周、1 月、1 年），非天粒度时分区边界可超出 4.2.3 所定数据特征边界；指令须允许插入超出最小最大值范围的分区列值（见 1.5.13）。
基表或辅助结构的多级分区仅当每级满足上述条件且每级仅引用一个上述分区字段时允许；若实现须披露细节。
1.5.5 数据在持久介质上的物理放置不可审计。**禁止**显式垂直分区数据的 SQL DDL，行须逻辑上表现为原子的列集合。（注释：不依赖显式分区指令的垂直分区允许；显式分区指令指将一行中列组分配到与该行其它列不同文件/磁盘/区的指令。）
1.5.6 除 1.5.7 规定外，不允许数据库对象（表、行、列）的逻辑复制。表的辅助数据结构的物理实现可涉及从表复制选定数据，前提：所有复制数据由 DBMS/OS/硬件管理；所有复制对所有数据操作透明；更新事务提交时数据修改反映到所有逻辑副本；所有副本随时保持完整 ACID 特性（见第 3 条）。
1.5.7 构成基表一列或多列数据逻辑复制的辅助数据结构（如索引、物化视图、汇总表、用于强制关系完整性约束的结构）须符合 1.5.6 规定，其定义创建指令受下列限制：每条指令最多引用一个基表、不得引用其它辅助结构；每条指令仅引用一个——1.4.2.2 列的列/列组（无论是否主键约束）、1.4.2.3 列的列/列组（无论是否外键约束）、或 1.3 中 date 类型列；每条指令可含显式允许列上的函数或表达式。TPC-H 脚本中禁止任何导致在辅助结构物化上述显式允许列之外列（或列上函数）的指令（DDL/会话选项/全局配置参数等），也禁止导致物化来自多表列的辅助结构。
注释：合规指令生成的辅助结构实现通常含指向基表行的内嵌指针或引用；透明使用 row ID 或基表主键值都可接受。辅助结构所需透明内嵌主键值的生成属主键列的允许物化。主键/外键列见 1.4.1。
1.5.8 表名应与 1.4.1 一致；与保留字冲突时可用分隔标识符或有意义的别名。
1.5.9 每张表的列集须包含 1.4 定义的全部列，不得增加列，但列顺序不限。
1.5.10 列名须与 1.4 一致。
1.5.11 每列须逻辑离散、可由数据管理器独立访问（如 C_ADDRESS 与 C_PHONE 不能实现为单个离散列 C_DATA 的两部分）。
1.5.12 每列须可由数据管理器作为单列访问（如 P_TYPE 不能实现为两离散列 P_TYPE1/P_TYPE2）。
1.5.13 数据库须允许插入符合 1.3 与 1.4 数据类型及可选约束定义的任意数据值。
注释1：虽刷新函数（见 2.5）不插入任意值、不修改所有表，但所有表须在整个性能测试期间可修改。
注释2：意在防止数据库模式定义不当利用数据库有限数据填充（另见 0.2 与 5.2.7）。

### 1.6 数据访问透明性要求

1.6.1 数据访问透明性是系统从查询文本中移除对分区数据位置与访问机制知识的特性。无有限测试序列能证明系统支持完全数据访问透明。下列要求描述建立系统提供透明数据访问所需的最小能力。使用水平分区的实现须满足 1.6.2 与 1.6.3 的透明数据访问要求。（注释：要求数据访问由市售层——交互式 SQL 接口、DBMS、OS、硬件或其组合——直接透明提供。）
1.6.2 1.4 所述各表须能以与表分区无关的名称标识。可执行查询文本（见 2.1.1.2）中所有数据操作只能用这些名称。
1.6.3 用满足 1.6.2 的名称，任意非 TPC-H 查询须能引用任意行或列集合：由底层 DBMS 支持的任意条件标识；用 1.6.2 所述名称、对所有表使用相同数据操作语义与语法。（注释：每个 TPC-H 查询使用通用机制访问数据库数据。）
