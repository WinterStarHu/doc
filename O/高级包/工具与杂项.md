## DBMS_ALERT
`DBMS_ALERT` 支持数据库事件（警报）的异步通知。通过适当使用此包和数据库触发器，应用程序可以在数据库中关注的值发生更改时通知自身。

- 安全模型
- 常量
- 限制

- DBMS_ALERT 子程序摘要
### DBMS_ALERT 概述
此场景描述了 DBMS_ALERT 包的一种可能用法。
假设某个图形工具正在显示来自数据库表中某些数据的图表。该图形工具在读取并绘制数据后，可以等待覆盖刚才所读数据的数据库警报（`WAITONE`）。当数据被任何其他用户更改时，该工具会自动唤醒。所需做的只是在数据库表上放置一个触发器，该触发器在触发时执行信号（`SIGNAL`）。
### DBMS_ALERT 安全模型
此包的安全性可以通过将此包的 `EXECUTE` 权限授予选定的用户或角色来控制。您可能希望在此包之上编写一个覆盖包，以限制所使用的警报名称。然后可以授予此覆盖包的 `EXECUTE` 权限，而不是此包的权限。
### DBMS_ALERT 常量
`DBMS_ALERT` 包使用本主题中列出和描述的常量。
表 17-1 DBMS_ALERT 常量
| 名称 | 类型 | 值 | 描述 |
|---|---|---|---|
| MAXWAIT | INTEGER | 86400000 | 等待警报的最长时间（1000 天，实质上相当于永远）。 |
### DBMS_ALERT 限制
由于数据库警报器会发出提交，因此它们不能与 Oracle Forms 一起使用。有关在 Oracle Forms 活动时调用存储过程的限制的更多信息，请参阅您的 Oracle Forms 文档。

### DBMS_ALERT 操作说明
本主题列出了与一般和特定应用程序相关的说明。此外，还提供了 DBMS_ALERT 错误消息列表。
- 警报是基于事务的。这意味着直到发出警报信号的事务提交后，等待的会话才会收到警报。对于给定的警报，可以有任意数量的并发信号发出者，也可以有任意数量的并发等待者。
- 等待的应用程序在数据库中被阻塞，无法执行任何其他工作。
- 应用程序可以注册多个事件，然后使用 WAITANY 过程等待其中任何一个发生。
````````
- 应用程序还可以向 WAITONE 或 WAITANY 过程提供一个可选的 timeout 参数。如果不存在挂起的警报，timeout 为 0 会立即返回。
- 发出信号的会话可以选择性地传递一条消息，该消息由等待的会话接收。
- 警报的发出频率可以高于相应的应用程序等待调用。在这种情况下，较早的警报将被丢弃。应用程序始终获取最新的警报（基于事务提交时间）。
- 如果应用程序不需要基于事务的警报，DBMS_PIPE 包可能提供一个有用的替代方案。另请参阅：DBMS_PIPE
- 如果在调用 SIGNAL 后事务回滚，则不会发生警报。
- 可能会接收到警报、读取数据，却发现数据没有变化。这是因为数据在先前警报之后、但在为该先前警报读取数据之前发生了更改。
  - 共享模式。如果您的数据库在共享模式下运行，则需要一个轮询循环来检查来自其他实例的警报。轮询循环默认为五秒，可以通过 SET_DEFAULTS 过程进行设置。
````
  - WAITANY 过程。如果您使用 WAITANY 过程，并且发出信号的会话发出了信号但未在信号发出后的一秒内提交，则需要一个轮询循环，以便此未提交的警报不会掩盖其他警报。轮询循环以一秒的间隔开始，并按指数规律退避到 30 秒的间隔。

### DBMS_ALERT 示例
在此示例中，假设您要绘制所有员工按部门划分的平均工资图表。您的应用程序需要在 `EMP` 发生更改时随时知晓。
您的应用程序类似于以下代码：
```
DBMS_ALERT.REGISTER('emp_table_alert');
    <<readagain>>:
   /* ... read the emp table and graph it */
      DBMS_ALERT.WAITONE('emp_table_alert', :message, :status);
      if status = 0 then goto <<readagain>>; else
      /* ... error condition */
```
`EMP` 表将具有类似于以下的触发器：
```
CREATE TRIGGER emptrig AFTER INSERT OR UPDATE OR DELETE ON emp
    BEGIN
      DBMS_ALERT.SIGNAL('emp_table_alert', 'message_text');
   END;
```
当应用程序对该警报不再感兴趣时，它会发出以下请求：
```
DBMS_ALERT.REMOVE('emp_table_alert');
```
这减少了警报信号发出者所需的工作量。如果会话在存在已注册的警报时退出（或死亡），该警报最终会被此包的未来用户清理。
该示例保证应用程序始终能看到最新的数据，尽管它可能无法看到每个中间值。

#### REGISTER 过程

该过程允许会话注册对某个告警的关注。
语法
```
DBMS_ALERT.REGISTER (
   name      IN  VARCHAR2,
   cleanup   IN  BOOLEAN DEFAULT TRUE);
```
参数
表 17-4 REGISTER 过程参数
| Parameter | Description |
|---|---|
| name | 本会话关注的告警名称 |
| cleanup | 指定是否清理 DBMS_ALERT 包使用的任何现存孤立管道。此清理仅在每个包实例化首次调用 REGISTER 时执行。该参数默认值为 TRUE。 |
警告：
以 'ORA$' 开头的告警名称保留供 Oracle 提供的产品使用。名称长度必须为 30 字节或更短。名称不区分大小写。
使用说明
一个会话可以注册关注无限数量的告警。当会话不再关注时，应通过调用 `REMOVE` 取消注册。

#### REMOVE 过程

该过程使不再对某个警报感兴趣的会话能够从其注册列表中移除该警报。移除警报可以减少警报发送方所需的工作量。

语法
```
DBMS_ALERT.REMOVE (
   name  IN  VARCHAR2);
```

参数
Table 17-5 REMOVE Procedure Parameters
| Parameter | Description |
|---|---|
| name | 要从注册列表中移除的警报名称（不区分大小写）。 |

使用说明
移除警报非常重要，因为它可以减少警报发送方所需的工作量。如果会话在未移除警报的情况下终止，该警报最终（但不会立即）会被清除。

#### REMOVEALL 过程

此过程从注册列表中移除本会话的所有警报。当会话不再关注任何警报时，应当执行此操作。
在会话期间首次引用此包时，会自动调用此过程。因此，之前可能异常终止的会话中的警报不会影响本会话。
此过程始终执行提交。
语法
```
DBMS_ALERT.REMOVEALL;
```

#### SIGNAL 过程

此过程发出警报。`SIGNAL` 调用的效果仅在执行该调用的事务提交时才会发生。如果事务回滚，则 `SIGNAL` 无效。
所有已注册关注此警报的会话都会收到通知。如果关注此警报的会话当前正在等待，则它们会被唤醒。如果关注此警报的会话当前未在等待，则会在它们下次执行等待调用时收到通知。
多个会话可以并发地对同一警报执行信号操作。每个会话在发出警报信号时，会阻塞所有其他并发会话，直到其提交。这起到了序列化事务的作用。
语法
```
DBMS_ALERT.SIGNAL (
   name     IN  VARCHAR2,
   message  IN  VARCHAR2);
```
参数
表 17-7 SIGNAL 过程参数
| Parameter | Description |
|---|---|
| name | 要发出信号的警报名称。 |
| message | 长度为 1800 字节或更短的消息，用于与此警报关联。此消息将传递给等待的会话。等待的会话或许能够利用消息中的信息，在警报发生后避免读取数据库。 |

#### WAITANY 过程

调用此过程可等待当前会话已注册的任意警报发生。
语法
```
DBMS_ALERT.WAITANY (
   name      OUT  VARCHAR2,
   message   OUT  VARCHAR2,
   status    OUT  INTEGER,
   timeout   IN   NUMBER DEFAULT MAXWAIT);
```
参数
Table 17-8 WAITANY Procedure Parameters
| Parameter | Description |
|---|---|
| name | 返回发生的警报的名称。 |
| message | 返回与警报关联的消息。这是由 SIGNAL 调用提供的消息。如果在此警报上发生多个 SIGNAL 调用后 WAITANY 才执行，则该消息对应于最近的 SIGNAL 调用。之前的 SIGNAL 调用的消息将被丢弃。 |
| status | 返回值：0 - 发生警报 1 - 发生超时 |
| timeout | 等待警报的最长时间。如果在 timeout 秒之前没有发生警报，则返回状态 1。 |
用法说明
在执行此过程之前会发出一个隐式 `COMMIT`。等待警报的同一会话也可以先发出警报信号。在这种情况下，请记住在发出信号之后、等待之前进行提交；否则，`DBMS_ALERT` 调用的 `DBMS_LOCK`.`REQUEST` 将返回状态 4。
异常
```
-20000, ORU-10024: there are no alerts registered.
```

#### WAITONE Procedure

此过程等待特定警报的发生。
在此过程执行之前会发出隐式 `COMMIT`。首先发出警报信号的会话也可以在后续事务中等待该警报。在这种情况下，请记住在 signal 之后且在 wait 之前执行 commit；否则，`DBMS_LOCK`.`REQUEST`（由 `DBMS_ALERT` 调用）将返回状态 4。
语法
```
DBMS_ALERT.WAITONE (
   name      IN   VARCHAR2,
   message   OUT  VARCHAR2,
   status    OUT  INTEGER,
   timeout   IN   NUMBER DEFAULT MAXWAIT);
```

## DBMS_APPLICATION_INFO
应用程序开发人员可以使用 `DBMS_APPLICATION_INFO` 包，配合 Oracle Trace 和 SQL 跟踪工具，在数据库中记录正在执行的模块或事务的名称，以便日后在跟踪各模块性能和调试时使用。

- Overview
- Security Model
- Operational Notes

### DBMS_APPLICATION_INFO Overview
注册应用程序后，系统管理员和性能调优专家就可以按模块跟踪性能。系统管理员还可以使用此信息按模块跟踪资源使用情况。当应用程序向数据库注册时，其名称和操作会记录在 `V$SESSION` 和 `V$SQLAREA` 视图中。
### DBMS_APPLICATION_INFO Security Model
无需更多权限。`DBMSAPIN.SQL` 脚本已作为标准数据库创建过程的一部分运行。

如果您想根据模块收集自己的统计数据，可以通过在另一个模式中编写该包的版本来实现此包的包装，该版本首先收集统计数据，然后调用 `SYS` 版本的包。随后可以将 `DBMS_APPLICATION_INFO` 的公共同义词更改为指向 DBA 版本的包。

#### SET_SESSION_LONGOPS 过程

此过程在 `V$SESSION_LONGOPS ` 视图中设置一行。这是一个用于指示长时间运行操作的持续进度的视图。某些 Oracle 功能（例如并行执行和服务器管理恢复）使用此视图中的行来指示诸如数据库备份等操作的状态。
应用程序可以使用 `SET_SESSION_LONGOPS` 过程来通告应用程序特定长时间运行任务的进度信息，以便可以通过 `V$SESSION_LONGOPS` 视图监控进度。
语法
```
DBMS_APPLICATION_INFO.SET_SESSION_LONGOPS (
   rindex      IN OUT BINARY_INTEGER,
   slno        IN OUT BINARY_INTEGER,
   op_name     IN     VARCHAR2       DEFAULT NULL,
   target      IN     BINARY_INTEGER DEFAULT 0,
   context     IN     BINARY_INTEGER DEFAULT 0,
   sofar       IN     NUMBER         DEFAULT 0,
   totalwork   IN     NUMBER         DEFAULT 0,
   target_desc IN     VARCHAR2       DEFAULT 'unknown target',
   units       IN     VARCHAR2       DEFAULT NULL)
set_session_longops_nohint constant BINARY_INTEGER := -1;
```
参数
表 21-7 SET_SESSION_LONGOPS 过程参数
| 参数 | 描述 |
|---|---|
| rindex | 表示要更新的 v$session_longops 行的标记。将其设置为 set_session_longops_nohint 可启动新行。使用先前调用返回的值可重用某一行。 |
| slno | 在对 set_session_longops 的多次调用之间保存信息：它供内部使用，不应由调用者修改。 |
| op_name | 指定长时间运行任务的名称。它显示为 v$session_longops 的 OPNAME 列。最大长度为 64 字节。 |
| target | 指定长时间运行操作期间正在处理的对象。例如，它可能是一个正在排序的表 ID。它显示为 v$session_longops 的 TARGET 列。 |
| context | 客户端想要存储的任何数字。它显示在 v$session_longops 的 CONTEXT 列中。 |
| sofar | 客户端想要存储的任何数字。它显示在 v$session_longops 的 SOFAR 列中。这通常是迄今为止已完成的工作量。 |
| totalwork | 客户端想要存储的任何数字。它显示在 v$session_longops 的 TOTALWORK 列中。这通常是此长时间运行操作中需要完成的总工作量的估计值。 |

示例
此示例在循环中对 10 个对象执行任务。当示例完成每个对象时，Oracle 会根据该过程的进度更新 `V$SESSION_LONGOPS `。
```
DECLARE
        rindex    BINARY_INTEGER;
        slno      BINARY_INTEGER;
        totalwork number;
        sofar     number;
        obj       BINARY_INTEGER;
      BEGIN
        rindex := dbms_application_info.set_session_longops_nohint;
        sofar := 0;
        totalwork := 10;
        WHILE sofar < 10 LOOP
          -- update obj based on sofar
          -- perform task on object target
          sofar := sofar + 1;
          dbms_application_info.set_session_longops(rindex, slno,
            "Operation X", obj, 0, sofar, totalwork, "table", "tables");
        END LOOP;
      END;
```

## DBMS_RANDOM
`DBMS_RANDOM` 包提供了一个内置的随机数生成器。`DBMS_RANDOM` 不适用于密码学。

### `DBMS_RANDOM` 不建议使用的子程序
这些子程序在 Oracle Database 11g 中已不建议使用。Oracle 建议您不要在新应用程序中使用不建议使用的过程。对不建议使用的功能的支持仅用于向后兼容。
- `INITIALIZE` Procedure
- `RANDOM` Function
- `TERMINATE` Procedure
### `DBMS_RANDOM` 安全模型
此包应作为 `SYS` 安装。默认情况下，该包使用当前用户名、精确到秒的当前时间以及当前会话进行初始化。Oracle 建议应为需要执行此包的用户显式授予 `EXECUTE` 权限，而不应依赖 `PUBLIC EXECUTE` 权限。
### `DBMS_RANDOM` 操作说明
这些操作说明适用于 `DBMS_RANDOM`。
- `DBMS_RANDOM.RANDOM` 生成 [-2^^31, 2^^31) 范围内的整数。
- `DBMS_RANDOM.VALUE` 生成 [0,1) 范围内具有 38 位精度的数字。
`DBMS_RANDOM` 可以被显式初始化，但在调用随机数生成器之前不需要进行初始化。如果未执行显式初始化，它将使用日期、用户 ID 和进程 ID 自动初始化。
如果此包使用相同的种子播种两次，然后以相同的方式访问，则在两种情况下将产生相同的结果。
在某些情况下（例如测试时），您可能希望每次运行时随机数序列都相同。在这种情况下，您可以通过调用 `DBMS_RANDOM.SEED` 的一个重载来使用常量值为生成器播种。若要使每次运行产生不同的输出，只需省略对 "Seed" 的调用，系统将为您选择合适的种子。

## UTL_RAW
`UTL_RAW` 包提供了用于操作 `RAW` 数据类型的 SQL 函数。
本章包含以下主题：
- 概览
- 操作说明

### UTL_RAW 概览
此包是必需的，因为普通 SQL 函数不能对 `RAWs` 进行操作，且 PL/SQL 不允许在 `RAW` 和 `CHAR` 数据类型之间进行重载。`UTL_RAW` 还包含将各种 COBOL 数字格式转换为 `RAWs` 以及从 `RAWs` 转换回各种 COBOL 数字格式的子程序。
`UTL_RAW` 并不专用于数据库环境，它实际上也可以在其他环境中使用。因此，该包使用了前缀 UTL，而不是 DBMS。
### UTL_RAW 操作说明
`UTL_RAW` 允许一个 `RAW` “记录”由许多元素组成。通过使用 `RAW` 数据类型，将不会执行字符集转换，从而在通过远程过程调用传输时使 `RAW` 保持其原始格式。
使用 `RAW` 函数，您可以操作以前仅限于 `hextoraw` 和 `rawtohex` 函数的二进制数据。
注意:
关于数据类型的说明：
``````
- PLS_INTEGER 和 BINARY_INTEGER 数据类型是相同的。本文档在参考信息（例如表类型、记录类型、子程序参数或子程序返回值）中使用 BINARY_INTEGER 来指示数据类型，但在讨论和示例中可能使用两者中的任何一个。
``````
- INTEGER 和 NUMBER(38) 数据类型也是相同的。本文档通篇使用 INTEGER。
````````

````
#### FREE_UNUSED_USER_MEMORY Procedure

本过程用于在执行需要大量内存（超过 100K）的操作后回收未使用的内存。
消耗大量内存的操作示例包括：
````
- 大规模排序，其中整个 sort_area_size 被耗尽，且 sort_area_size 高达数百 KB。
- 编译大型 PL/SQL 包、过程或函数。
- 在 PL/SQL 索引表中存储数百 KB 的数据。
可以通过跟踪 `v$sesstat` 或 `v$statname` 固定视图中的 "session UGA memory" 和 "session PGA memory" 统计信息来监控用户内存。监控这些统计信息还可以显示本过程已释放了多少内存。
注意：
本过程仅应在内存极为紧张的情况下使用。应谨慎且少频率地使用。
语法
```
DBMS_SESSION.FREE_UNUSED_USER_MEMORY;
```
返回值
本过程的行为取决于代表客户端运行的服务器的配置：
- 专用服务器：将未使用的 PGA 内存和会话内存返还给操作系统。在此配置中，会话内存是从 PGA 分配的。
````
- 共享服务器：将未使用的会话内存返还给 shared_pool。在此配置中，会话内存是从 shared_pool 分配的。
使用说明
为了使用本过程释放内存，该内存必须处于未使用状态。
在操作分配内存后，只有相同类型的操作才能复用已分配的内存。例如，为排序分配内存后，即使排序已完成且内存不再被使用，也只有另一次排序才能复用为排序分配的内存。对于排序和编译，在操作完成后，内存不再被使用，用户可以调用本过程来释放未使用的内存。
索引表会隐式分配内存来存储赋予索引表元素的值。因此，索引表中的元素越多，RDBMS 为该索引表分配的内存就越多。只要索引表中存在元素，与该索引表关联的内存就处于使用状态。
索引表的作用域决定了其内存保持使用状态的时间长度。全局声明的索引表是指在包或包体中声明的索引表。它们从会话内存中分配内存。对于全局声明的索引表，其内存在用户登录的整个生命周期（用户会话的生命周期）内保持使用状态，并在用户断开与 ORACLE 的连接后被释放。
局部声明的索引表是指在函数、过程或匿名块内声明的索引表。这些索引表从 PGA 内存中分配内存。对于局部声明的索引表，只要用户仍在运行声明该索引表的过程、函数或匿名块，其内存就保持使用状态。在过程、函数或匿名块运行结束后，该内存即可供其他局部声明的索引表使用（换言之，该内存不再处于使用状态）。
将一个未初始化的“空”索引表赋值给现有索引表是一种显式重新初始化索引表及其关联内存的方法。此操作后，与该索引表关联的内存不再被使用，从而可以通过调用本过程将其释放。对于在用户会话生命周期内可能会不断增长的全局声明索引表，只要用户不再需要该索引表的内容，此方法就尤为实用。
与索引表作用域关联的内存规则依然适用；然而，此方法和本过程允许用户介入并显式释放与索引表关联的内存。
示例
以下 PL/SQL 说明了该方法以及 `FREE_UNUSED_USER_MEMORY` 过程的使用。
```
CREATE PACKAGE foobar
   type number_idx_tbl is table of number indexed by binary_integer;
   store1_table  number_idx_tbl;     --  PL/SQL indexed table
   store2_table  number_idx_tbl;     --  PL/SQL indexed table
   store3_table  number_idx_tbl;     --  PL/SQL indexed table
   ...
END;            --  end of foobar
DECLARE
   ...
   empty_table   number_idx_tbl;     --  uninitialized ("empty") version
BEGIN
   FOR i in 1..1000000 loop
     store1_table(i) := i;           --  load data
   END LOOP;
   ...
   store1_table := empty_table;      --  "truncate" the indexed table
   ...
   -
   dbms_session.free_unused_user_memory;  -- give memory back to system
   store1_table(1) := 100;           --  index tables still declared;
   store2_table(2) := 200;           --  but truncated.
   ...
END;
```

#### MODIFY_PACKAGE_STATE 过程

此过程用于对会话中活动的所有 PL/SQL 程序单元的会话状态执行各种操作（由 `action_flags` 参数指定）。此操作在发起当前调用的 PL/SQL 调用完成运行后生效。
此过程使用表 162-15 中列出的 `DBMS_SESSION` 常量。
语法
```
DBMS_SESSION.MODIFY_PACKAGE_STATE(
   action_flags IN PLS_INTEGER);
```
参数
表 162-14 MODIFY_PACKAGE_STATE 过程参数
| 参数 | 描述 |
|---|---|
| action_flags | 决定对 PL/SQL 程序单元所采取操作的位标志：DBMS_SESSION.FREE_ALL_RESOURCES (或 1)—从会话中释放与每个先前运行的 PL/SQL 程序关联的所有内存。清除任何包全局变量的当前值并关闭缓存的游标。在后续使用时，PL/SQL 程序单元将被重新实例化，并且包全局变量将被重新初始化。使用 DBMS_SESSION.FREE_ALL_RESOURCES 参数调用 MODIFY_PACKAGE_STATE 提供的功能与 DBMS_SESSION.RESET_PACKAGE() 接口完全相同。DBMS_SESSION.REINITIALIZE (或 2)—重新初始化包，而无需实际释放并从头重新创建。而是重用包内存。就程序语义而言，DBMS_SESSION.REINITIALIZE 标志类似于 DBMS_SESSION.FREE_ALL_RESOURCES 标志，因为两者都具有重新初始化所有包的效果。但是，DBMS_SESSION.REINITIALIZE 应表现出比 DBMS_SESSION.FREE_ALL_RESOURCES 选项更好的性能，因为：包被重新初始化，而无需实际释放并从头重新创建。而是重用包内存。从语义上讲，任何打开的游标都会被关闭。但是，游标资源实际上并未释放。它只是被返回到 PL/SQL 游标缓存中。游标缓存不会被刷新。因此，对应于 PL/SQL 中频繁访问的静态 SQL 的游标仍会缓存在 PL/SQL 游标缓存中，应用程序在后续使用这些语句时不会产生打开、解析和关闭新游标的开销。没有全局状态（如类型、存储过程）的 PL/SQL 模块的会话内存不会被释放并重新创建。 |
使用说明
有关标志之间的差异以及为何 `DBMS_SESSION.REINITIALIZE` 表现出比 `DBMS_SESSION.FREE_ALL_RESOURCES` 更好性能的原因，请参阅表 162-17 中的参数描述。
表 162-15 MODIFY_PACKAGE_STATE 的 Action_flags 常量
| 常量 | 描述 |
|---|---|
| FREE_ALL_RESOURCES | PLS_INTEGER:= 1 |
| REINITIALIZE | PLS_INTEGER:= 2 |
- 重新初始化是指将所有包变量重置为其初始值并运行包体中的初始化块（如果有）的过程。考虑以下包：
```

      n number;
      m number := P2.foo;
      d date := SYSDATE;
      cursor c is select * from emp;
      procedure bar;
    end P;
    /
    package body P is
      v   varchar2(20) := 'hello';
      procedure bar is
      begin
        ...
      end;
      procedure init_pkg is
      begin
        ....
      end;
    begin
      -- initialization block
      init_pkg;
      ...
      ...
    end P;
    /
```
对于包 P，重新初始化包括：
````
- Setting P.n to NULL
``````
- Invoking function P2.foo and setting P.m to the value returned from P2.foo
````
- Setting P.d to the return value of SYSDATE built-in
- Closing cursor P.c if it was previously opened
- Setting P.v to 'hello'
- Running the initialization block in the package body
- The reinitialization for a package is done only if the package is actually referenced subsequently. Furthermore, the packages are reinitialized in the order in which they are referenced subsequently.
````
- 当使用 FREE_ALL_RESOURCES 或 REINITIALIZE 时，请确保重置包变量值不会影响应用程序。
``````````
- 由于 DBMS_SESSION.REINITIALIZE 实际上不会导致所有包状态被释放，在某些情况下，与使用 FREE_ALL_RESOURCES 标志或 RESET_PACKAGE 过程相比，应用程序可能会消耗明显更多的会话内存。例如，在执行 DBMS_SESSION.MODIFY_PACKAGE_STATE(DBMS_SESSION.REINITIALIZE) 之后，如果应用程序不再引用许多以前引用过的包，那么这些包的会话内存将一直保留到会话结束（或直到调用 DBMS_SESSION.RESET_PACKAGE）。
````

此示例说明了 `DBMS_SESSION.MODIFY_PACKAGE_STATE` 的用法。考虑一个带有某些全局状态（游标 `c` 和数字 `cnt`）的包 `P`。当首次初始化包时，包变量 `cnt` 为 `0`，游标 `c` 为 `CLOSED`。然后，在该会话中，将 `cnt` 的值更改为 `111`，并对游标执行 `OPEN` 操作。如果调用 `print_status` 来显示包的状态，您会看到 `cnt` 为 `111` 并且游标为 `OPEN`。接着，调用 `DBMS_SESSION.MODIFY_PACKAGE_STATE`。如果再次使用 `print_status` 打印包 `P` 的状态，您会看到 `cnt` 再次变为 `0` 并且游标为 `CLOSED`。如果未调用 `DBMS_SESSION.MODIFY_PACKAGE_STATE`，则第二次 `print_status` 将输出 `111` 和 `OPEN`。

  5  end;

PL/SQL procedure successfully completed.

  3  end;

#### RESET_PACKAGE 过程

此过程取消实例化本会话中的所有包。它释放包状态。
注意：
参见 "SESSION _TRACE_ENABLE Procedure" 。 Oracle9i 中引入的 MODIFY_PACKAGE_STATE 接口提供了与 RESET_PACKAGE 等效的功能。它是一种高效的、更轻量的变体，用于重新初始化会话中所有 PL/SQL 包的状态。
用于缓存执行状态的内存与会话中运行过的所有 PL/SQL 函数、过程和包相关联。
对于包，这块内存保存了包变量的当前值，并控制由相应 PL/SQL 程序打开的游标的缓存。调用 `RESET_PACKAGE` 会从会话中释放与先前运行的每个 PL/SQL 程序关联的内存，因此，会清除所有包全局变量的当前值并关闭所有缓存的游标。
`RESET_PACKAGE` 还可用于在会话中可靠地重启失败的程序。如果包含包变量的程序失败，则很难确定哪些变量需要重新初始化。`RESET_PACKAGE` 保证所有包变量都重置为其初始值。
语法
```
DBMS_SESSION.RESET_PACKAGE;
```
使用说明
由于所有已执行的 PL/SQL 消耗的内存量可能变得很大，您可以在数据库应用程序的特定时刻使用 `RESET_PACKAGE` 来缩减会话内存占用。但是，请确保重置包变量值不会影响应用程序。此外，请记住，后续执行丢失了缓存内存和游标的程序时，速度会变慢，因为它们需要重新创建已释放的内存和游标。
`RESET_PACKAGE` 在调用时不会立即释放内存、游标和包变量。
注意：
`RESET_PACKAGE` 仅在发起调用的 PL/SQL 调用结束运行后，才会释放内存、游标和包变量。
例如，PL/SQL 过程 `P1` 调用 PL/SQL 过程 `P2`，而 `P2` 调用 `RESET_PACKAGE` 。直到过程 `P1` 结束执行（PL/SQL 调用结束），`RESET_PACKAGE` 的效果才会发生。
示例
此 SQL*Plus 脚本运行一个包含许多 PL/SQL 程序单元的大型程序，这些程序单元可能使用也可能不使用全局变量，但在此执行之后不再需要它们：
```
EXCECUTE large_plsql_program1;
```
要释放 PL/SQL 缓存的会话内存：
```
EXECUTE DBMS_SESSION.RESET_PACKAGE;
```
要运行另一个大型程序：
```
EXECUTE large_plsql_program2;
```
````

``````
- 上下文值的任何更改都会立即反映出来，随后通过 SYS_CONTEXT 访问该值的调用将返回最新值。
````````

#### SWITCH_CURRENT_CONSUMER_GROUP 过程

此过程更改用户当前会话的当前资源消费者组。
如果用户拥有某个特定组的切换权限，则允许切换到该消费者组。如果调用者是另一个过程，则使用户能够切换到该过程所有者拥有切换权限的消费者组。
语法
```
DBMS_SESSION.switch_current_consumer_group (
   new_consumer_group     IN  VARCHAR2,
   old_consumer_group     OUT VARCHAR2,
   initial_group_on_error IN  BOOLEAN);
```
参数
表 162-25 SWITCH_CURRENT_CONSUMER_GROUP 过程参数
| 参数 | 描述 |
|---|---|
| new_consumer_group | 要切换到的消费者组的名称 |
| old_consumer_group | 刚切换出的消费者组的名称 |
| initial_group_on_error | 如果为 TRUE，则在发生错误时将调用者的当前消费者组设置为其初始消费者组 |
返回值
此过程在参数 `old_consumer_group` 中输出用户的旧消费者组。
注意：
                              - old_consumer_group 参数仅在显式设置时才返回旧消费者组的名称。也就是说，如果旧消费者组是由某些映射规则设置的，则可能会得到 NULL。
                              - 稍后可以使用在 old_consumer_group 中返回的值切换回旧消费者组。
异常
表 162-26 SWITCH_CURRENT_CONSUMER_GROUP 过程异常
| 异常 | 描述 |
|---|---|
| 29368 | 不存在的消费者组 |
| 1031 | 权限不足 |
| 29396 | 无法切换到 OTHER_GROUPS 消费者组 |
使用说明
过程所有者必须对用户切换出的组（`old_consumer_group`）拥有权限才能将用户切换回去。有一个例外：该过程始终可以将用户切换回其初始消费者组（跳过权限检查）。
通过将 `initial_group_on_error` 设置为 `TRUE`，如果 `SWITCH_CURRENT_CONSUMER_GROUP` 无法将其放入 `new_consumer_group` 指定的组，则会将当前会话放入默认组。即使当前消费者组已更改为初始消费者组，与尝试将会话移入 `new_consumer_group` 相关的错误仍会引发。
示例
```
CREATE OR REPLACE PROCEDURE high_priority_task is
   old_group varchar2(30);
   prev_group varchar2(30);
   curr_user varchar2(30);
BEGIN
  -- 将调用者切换到特权消费者组。如果我们做不到，就会抛出
  -- 错误，但消费者组不会改变
  -- 因为 'initial_group_on_error' 设置为 FALSE
  dbms_session.switch_current_consumer_group('tkrogrp1', old_group, FALSE);
  -- 设置异常处理程序（在发生错误时，我们不希望
  -- 在让会话仍处于特权
  -- 组中的情况下返回给调用者）
  BEGIN
    -- 在特权组下执行一些操作
  EXCEPTION
    WHEN OTHERS THEN
     -- 过程所有者可能没有
     -- old_group 的权限。'initial_group_on_error' 设置为 TRUE 以确保
     -- 在这种
     -- 情况下将用户移出特权组
     dbms_session.switch_current_consumer_group(old_group,prev_group,TRUE);
     RAISE;
    END;
  -- 我们成功了。现在切换到 old_group，或者如果做不到，则切换
  -- 到调用者的初始消费者组
  dbms_session.switch_current_consumer_group(old_group,prev_group,TRUE);
END high_priority_task;
/
```

#### INVALIDATE 过程

此过程使数据库对象失效，并（可选）修改其 PL/SQL 编译器参数设置。它还会使（直接或间接）依赖于正在失效对象的任何对象失效。
语法
```
DBMS_UTILITY.INVALIDATE (
   p_object_id              NUMBER,
   p_plsql_object_settings  VARCHAR2 DEFAULT NULL,
   p_option_flags           PLS_INTEGER DEFAULT 0);
```
参数
Table 196-27 INVALIDATE 过程参数
| Parameter | Description |
|---|---|
| p_object_id | 要失效的对象的 ID 编号。这与 ALL_OBJECTS 中 OBJECT_ID 列的值相同。如果 object_id 参数为 NULL 或无效，则会引发异常 inv_not_exist_or_no_priv。此过程的调用者必须对正在失效的对象具有 create 权限，否则会引发 inv_not_exist_or_no_priv 异常。 |
| p_plsql_object_settings | 可选参数，如果 p_object_id 指定的对象不是 PL/SQL 对象，则忽略此参数。如果未为此参数指定值，则 PL/SQL 编译器设置保持不变，即等同于 REUSE SETTINGS。如果提供了值，则必须指定由一个或多个空格分隔的 PL/SQL 编译器设置的值。每个设置只能指定一次，否则会引发 inv_malformed_settings 异常。设置值仅针对 p_object_id 指定的对象进行更改，不会影响可能失效的依赖对象。设置名称和值不区分大小写。如果省略了某个设置并且指定了 REUSE SETTINGS，那么如果在先前编译此库单元时为该编译器设置指定了值，Oracle Database 将使用先前的值。如果省略了某个设置且未指定 REUSE SETTINGS，或者在先前的编译中未为该参数指定值，则数据库将从会话环境中获取该设置的值。 |
| p_option_flags | 可选参数，默认值为零（无标志）。invalidate 支持的选项标志。inv_error_on_restrictions（参见 Constants）：子程序对可失效的对象施加了各种限制。例如，p_object_id 指定的对象不能是表。默认情况下，invalidate 在这些条件下会静默返回（并且不引发异常）。如果调用者设置了此标志，则会引发异常 inv_restricted_object。 |
异常
Table 196-27 INVALIDATE 异常
| Exception | Description |
|---|---|
| INV_NOT_EXIST_OR_NO_PRIV | 当 object_id 参数为 NULL 或无效，或者当调用者对正在失效的对象没有 CREATE 权限时引发 |
| INV_MALFORMED_SETTINGS | 如果在 p_plsql_object_settings 参数中多次指定某个编译器设置时引发 |
| INV_RESTRICTED_OBJECT | 当违反与 p_object_id 参数相关的不同条件组合时引发 |
用法说明
由 `p_object_id` 指定的对象的对象类型（`ALL_OBJECTS` 中的 `object_type` 列）必须是 `PROCEDURE`、`FUNCTION`、`PACKAGE`、`PACKAGE` `BODY`、`TRIGGER`、`TYPE`、`TYPE` `BODY`、`LIBRARY`、`VIEW`、`OPERATOR`、`SYNONYM` 或 `JAVA` `CLASS`。如果对象不是这些类型之一，并且在 `p_option_flags` 中指定了 `inv_error_on_restrictions` 标志，则会引发异常 `inv_restricted_object`，否则不会采取任何操作。
如果由 `p_object_id` 指定的对象是 `STANDARD`、`DBMS_STANDARD` 的包规范，或者是 `DBMS_UTILITY` 的规范或包体，并且在 `p_option_flags` 中指定了 `inv_error_on_restrictions` 标志，则会引发异常 `inv_restricted_object`，否则不会采取任何操作。
如果由 `p_object_id` 指定的对象是对象类型规范，并且存在依赖于该类型的表，而且在 `p_option_flags` 中指定了 `inv_error_on_restrictions` 标志，则会引发异常 `inv_restricted_object`，否则不会采取任何操作。
示例
Example 1
```
DBMS_UTILITY.INVALIDATE (1232, 'PLSQL_OPTIMIZE_LEVEL = 2 REUSE SETTINGS');
```
假设 `object_id` 1232 指的是 `HR` 模式中的 `remove_emp` 过程。那么上述调用会将 remove_emp 过程标记为无效，并将其 `PLSQL_OPTIMIZE_LEVEL` 编译器设置更改为 2。由于指定了 `REUSE` `SETTINGS`，其他编译器设置的值将保持不变。
依赖于 `hr`.`remove_emp` 的对象也将被标记为无效。它们的编译器参数不会被更改。
Example 2
```
DBMS_UTILITY.INVALIDATE (40775, 'plsql_code_type = native');
```
假设 `object_id` 40775 指的是 `OE` 模式中的类型体 `leaf_category_typ`。那么上述调用会将该类型体标记为无效，并将其 `PLSQL_CODE_TYPE` 编译器设置更改为 `NATIVE`。由于未指定 `REUSE` `SETTINGS`，其他编译器设置的值将从当前会话环境中获取。
由于没有对象可以依赖于类型体，因此不会产生级联失效。
Example 3
```
DBMS_UTILITY.INVALIDATE (40796);
```
假设 `object_id` 40796 指的是 `OE` 模式中的视图 `oc_orders`。那么上述调用会将 `oc_orders` 视图标记为无效。
依赖于 `oe`.`oc_orders` 的对象也将被标记为无效。
